# 开发侧评测（dev）：入口层对「改这个仓库的 agent」到底有没有用

[`TRIGGER-EVAL.md`](TRIGGER-EVAL.md) 量的是 **B 轨**（用这个工具分析 kernel 的 agent）：
给一段真实诉求 + 工具目录，它会不会选我们、会不会编子命令。
这一份量的是 **A 轨**（改这个仓库的 agent）：**它找不找得到"该改哪儿、要重跑什么"**。

为什么要单独量：`AGENTS.md` 是开发 agent 唯一会自动加载的那份文件，它此前写的却是
"怎么用这个工具"（三步闭环 + 读数字的硬规则），细节指针指向使用面文档，**完全没提
`CONTRIBUTING.md`**。"入口层有用"在那时是断言，不是数。

## 1 协议

* **被测提交**：改动前 `b25626c`，改动后 `cc96303`（两轮都从该提交 `git clone` 一个干净副本）。
* **被测 agent 看到的东西**：任务本身 + 一段"进入仓库时收到的全部仓库级指令"
  （即该提交的 `AGENTS.md` 全文，**逐字引用**）。不给任何其它导引，也不告诉它文件在哪。
  真实运行时这份文件由 harness 自动加载（Codex / Cursor / Copilot 同理）；评测里改成
  显式给出，是为了让两轮可比、可复现。
* **任务**（三个，覆盖三类典型改动）：

  | # | 任务 | 期望的单一真源 | 期望重跑的生成物 |
  |---|---|---|---|
  | T1 | 新增一种拒绝情形 `device_memory_pressure`（要有标题、补救办法、参考层里能查到） | `refusals.py` | `references/refusal-codes.md` |
  | T2 | 新增一个能力问题 `shared_memory_bank_conflicts`（必然被拒，要说明改问什么） | `capabilities.py` | `COVERAGE.md`、`eval/tasks/*.json` |
  | T3 | 仓库里有测试红了，修好它（公开数字必须能追到产物，不许动断言） | `README.md`（数字来自产物） | — |

  T3 的"红"是注入的：把 README 里跨运行并集从产物算出的 `−4.3% ~ +12.7%` 改成 `+11.7%`，
  只影响一条测试（`test_documented_union_band_matches_all_registered_artifacts`）。
* **取证**：三处交叉——agent 自报的完整命令序列、副本里的 `git status/diff`、最后一次测试汇总行。

  | 指标 | 定义 |
  |---|---|
  | `entry_layer_rate` | 第一条调查动作就走入口层（`tools/dev_index.py --brief`，或按 `AGENTS.md` 指到 `CONTRIBUTING.md` 索引）的比例 |
  | `route_rate` | 动了**正确**的单一真源的比例 |
  | `regen_rate` | 受影响的生成物**重跑生成器**（而不是手改生成物）的比例 |
  | `gate_rate` | 最后跑了全量门禁（`pytest` / `dev_index.py --gates`）的比例 |
  | `extra_files` | 超出任务最小集合的改动文件数（含新建） |

## 2 结果

| 任务 | 轮 | 命令数 | entry_layer | route | regen | gate | extra_files |
|---|---|---|---|---|---|---|---|
| T1 拒绝码 | A（改前） | 42 | ✗ | ✓ | ✓ | ✓ pytest | **11**（含新建 3 个测试文件、1 个新 CLI 开关） |
| T1 拒绝码 | B（改后） | 26 | **✓** | ✓ | ✓ | **✓ `--gates` 7/7** | **3** |
| T2 能力问题 | A | 43 | ✗ | ✓ | ✓ | ✓ pytest | 10（其中 5 个是当时**漂移**的 eval 任务文件） |
| T2 能力问题 | B | 38 | **✓** | ✓ | ✓ | **✓ `--gates` 7/7** | 4（eval 任务只动了受影响的 1 个） |
| T3 修红测试 | A | 15 | ✗ | ✓ | — | ✓ pytest | 1 |
| T3 修红测试 | B | 13 | **✓** | ✓ | — | **✓ `--gates` 7/7** | 1 |
| **合计** | A | **100** | **0/3** | 3/3 | 2/2 | 3/3 | **22** |
| **合计** | B | **77** | **3/3** | 3/3 | 2/2 | 3/3 | **8** |

三个结论：

1. **agent 本来就找得到真源**（`route_rate` 两轮都是 3/3）。入口层的价值不在"救笨"，
   而在**成本**与**边界**：命令数 −23%、超范围文件 −64%，而且改后三轮都主动跑了
   `--gates`（改前没有一轮知道有这条命令，只有 pytest）。
2. **入口层改变了"范围"的定义方式**。T1 两轮的差别最清楚：改前那个 agent 从
   `refusals.py` 的 docstring 出发，自行判断"要真的能拒绝"，于是实现了整套 NVML
   `memory.free` 采样 + 一个新开关 `--ks-required-mem-mb` + 3 个测试文件；改后那个 agent
   按索引的 `加一种拒绝理由 → refusals.py → 重跑 gen_agent_refs.py` 做最小改动（3 个文件），
   并把"还没接到运行路径上"当作**需要告知的缺口**写了出来。前者多做了没人要的接口，
   后者少做了任务开头暗示的行为 —— 这正是"规范必须说清登记一个 code 与用它拒绝是两件事"，
   已补进 `CONTRIBUTING.md` §⑤。
3. **它顺带修掉了一个真缺陷，并且这个缺陷的修复本身可度量**：改前 T2 发现
   `eval/make_tasks.py --check` 在仓库里就是红的（决策包升到 v1.1 后没人重跑），
   于是 5 个任务文件全被重写；改后同一个任务只动了受影响的 1 个文件。

## 3 没被入口层解决的事（同样重要）

* **ncu 计数器名仍然是"声明但从未核实"**。T2 两轮都把
  `l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum` 这类名字写进了代码/文档；
  两轮都**符合仓库既有做法**（`capabilities.QUESTIONS` 的 `outputs` 与 README 的迁移表
  本来就直列 ncu 名字），但本机没有 `ncu`，谁也无法核实。这是仓库级缺口，不是 agent 的错。
  下次上真机时一条 `ncu --query-metrics` 就能把这些名字变成可核实的清单（并加一条门禁）。
* **T2 的命令数只降了 12%**。它的探索主要花在"这个问题该判 refused 还是 degraded"这类
  **语义判断**上，那不是索引能替代的 —— 索引能省的是"找文件"，省不了"想清楚"。

## 4 边界与限制（必须一起读）

* **n = 3，且每个任务只跑 1 次**。这是方向性证据，不是统计结论。
* **两轮之间除了入口层还动了别的东西**：`pyproject.toml` 去掉了 `addopts = "-q"`
  （`-q` 叠 `-q` 会吞掉汇总行）。改前 T3 有 4 条命令纯粹在绕这个坑，所以"命令数下降"
  有一部分不是入口层的功劳。
* **同一个模型、同一套 harness**，不是"不同 agent 的对照"。
* **A 轨的失败模式没有全部被覆盖**：这三个任务都没触发"手改生成物"或"`git add -f docs`"
  这类违规，所以违规率这一栏是空的 —— 不能据此说"改后不会违规"。
